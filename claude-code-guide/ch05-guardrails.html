ガードレール機能

モデルは指示を必ず守るとは限らない。ガードレールは、モデルが誤っても被害が出ないように、ハーネスがツール実行の直前で許可・拒否する仕組みである。本章はその手段を整理する。

5-1. ツール使用（Tool Use）

モデルはテキストを返すだけで、何も実行しない。実行するのはハーネス（Claude Code 本体）である。

ツール使用は、モデルが JSON でツールと引数を指定し、ハーネスが実行して結果を返す往復である。本章の制御手段はすべて、この往復の途中に入る。

モデル → ハーネス（レスポンスの中の 1 ブロック）

{
  "type": "tool_use",
  "id": "toolu_01",               // 結果と突き合わせる ID
  "name": "Bash",                 // tools に載っているツール名
  "input": {                      // ツールごとの JSON Schema に従う引数
    "command": "npm test"
  }
}

ハーネス → モデル（次のリクエストの messages 末尾）

{
  "type": "tool_result",
  "tool_use_id": "toolu_01",
  "content": "PASS 12 tests",     // 実行結果、または拒否の理由
  "is_error": false
}
  • モデルが使えるツールは、ハーネスが tools に載せたものだけ
  • 結果は文字列で返る。成功か失敗かはモデルが読んで判断する。拒否の理由を返せば、モデルは別の手を選ぶ

独自ツールと MCP の違い

種類モデルからの呼び方制御手段
独自ツール（スクリプト・CLI・スキル）Bash の引数にコマンドを書くBash(…) ルール、フック、サンドボックス
MCP サーバー専用のツール定義が tools に増えるmcp__… ルール、フック（本資料の範囲外）

独自ツールは Bash 経由で実行されるので、制御も Bash と同じである。往復の記録は ~/.claude/projects/ の jsonl に残る。対話中は Ctrl+O で見られる。

5-2. ガードレールの全体像

公式ドキュメントは「権限ルールを強制するのは Claude Code であってモデルではない」としている。制御手段は、モデルに読ませる指示と、ハーネスが判定する強制の 2 つに分かれる。

種類手段誰が効かせるか
指示（ソフト制御）CLAUDE.md、rules、スキル、プロンプト、自動メモリモデル。読んで従う。保証はない
強制（ハード制御）権限ルール、権限モード、サンドボックス、フック、管理設定ハーネスと OS。ツール呼び出しの直前に、モデルの判断を経ずに判定する

図 5-2 のハーネスと OS の中では、ツール呼び出し 1 回ごとに次の順で判定が走る。途中で拒否されれば実行されない。

破られると困る規則は強制に、守られるのが望ましい指針は指示に書く。「.env を読むな」は、CLAUDE.md に書けば指示、Read(./.env) を deny に書けば強制である。自動メモリも指示の側である。公式は「確実に止めるには PreToolUse フックを使う」としている。

5-3. 権限ルール（Permission rules）

権限ルールは、「どのツールの、どの対象を、許可・確認・拒否するか」を設定ファイルに書いたものである。書式は ツール名 または ツール名(対象)。判定順は deny → ask → allow で、最初に一致したルールが結果を決める。

{
  "permissions": {
    "allow": [                                  // 確認なしで実行
      "Bash(npm run test *)",
      "Read(./src/**)"
    ],
    "ask": [                                    // 毎回ユーザー確認
      "Bash(git push *)"
    ],
    "deny": [                                   // 常に拒否。モデルには拒否の文面が返る
      "Read(./.env)",
      "WebFetch(domain:internal.example.com)"
    ],
    "defaultMode": "acceptEdits"                // どのルールにも一致しないときの動作
  }
}
書き方意味
BashBash のすべての呼び出し。deny に書くとツール自体がモデルから見えなくなる
Bash(npm run build)コマンドの完全一致
Bash(npm run test *)前方一致。引数付きを許す基本形
Read(./.env) / Edit(src/**)パス。gitignore と同じ glob
Read(~/.ssh/**) / Read(//etc/**)~/ はホーム、// は絶対パス。/ 1 本は設定ファイルの置き場所を基準にした相対パスで、/etc を指さない
Bash(command:rm *)✕ 無効。Bash(rm *) と書く

パイプや && で連結したコマンドは部分ごとに照合される。ls src | rm * が確認なしで通るには、ls と rm * の両方が許可されている必要がある。deny / ask はどれか 1 つの部分に一致すれば効く。

書く場所

スコープ（上ほど優先）ファイル影響範囲
Managed（管理設定）managed-settings.json組織の全ユーザー。管理者が配布
Local（ローカル設定）.claude/settings.local.json自分だけ・このリポジトリ。Claude Code が作れば git 管理外、手で作るなら .gitignore に追加
Project（プロジェクト設定）.claude/settings.json全員・このリポジトリ。コミット対象
User（ユーザー設定）~/.claude/settings.json自分だけ・全プロジェクト

権限ルールやフックの各設定は、上位が下位を置き換えるのではなくすべて連結される。チーム共通の設定は Project に、個人の追加分は Local に書く。有効な設定は /permissions で見る。

ルールと別に組み込まれている制限

  • 保護パス：.git・.claude などへの書き込みは、allow や acceptEdits で確認を省いていても自動承認されない（default / acceptEdits では確認、auto では分類器、dontAsk では拒否。bypass では通る）。モデルが自分の制限を書き換えないための仕組み
  • 読み取り専用コマンド：ls・cat・grep・git status などは常に確認なし。止めたいものは deny / ask に書く
  • 作業ディレクトリの外：ファイルの書き込みには確認が出る。拒否したいときは次の設定を書く
{
  "permissions": {
    // 作業ディレクトリの外への Write / Edit / NotebookEdit を拒否する。bypassPermissions を含む全モードで有効。Bash・MCP・フックは対象外
    "blockWritesOutsideWorkingDirectories": true
  }
}
権限ルールの限界
  • allow は deny に勝てない。Bash(aws *) を deny したまま Bash(aws s3 ls) だけ許可することはできない
  • 見ているのはコマンドの文字列だけ。変数展開や bash -c '…' の中身は読めない。確実に止めるにはフックを使う
  • スクリプトが自分で開くファイルも見えない。これを止められるのはサンドボックスだけ

5-4. 権限モード（Permission modes）

権限モードは、どの権限ルールにも一致しなかったツール呼び出しをどう扱うかを決める。指定方法は 3 つ。

  • 設定ファイル：permissions.defaultMode
  • 起動時：--permission-mode（設定ファイルより優先）
  • セッション中：切り替え可能
モード権限ルールフォールバック（既定動作）
denyaskallow
bypassPermissions
すべて通す		拒否ユーザー確認実行実行
auto
分類器に任せる		拒否ユーザー確認実行分類器が判断
dontAsk
確認せずに拒否		拒否拒否実行拒否
acceptEdits
編集まで通す		拒否ユーザー確認実行読み取り・編集・mkdir mv などのファイル操作は実行。ほかはユーザー確認
default
読み取りだけ通す		拒否ユーザー確認実行読み取りは実行。ほかはユーザー確認
plan
計画のみ		拒否ユーザー確認実行読み取りは実行。編集は拒否。ほかはユーザー確認

何も指定しなければ、対話ターミナルと VS Code では auto、-p（非対話実行）では default で始まる。auto と bypassPermissions を defaultMode に書けるのはユーザー設定と管理設定だけである。プロジェクト設定・ローカル設定に書いても無視される。

auto モードの分類器

auto では、ユーザーの代わりに別のモデル（分類器）が、各操作を実行してよいか実行前に判断する。

  • コスト：審査はサーバー側で行われ、追加課金なし（順次展開中）。対象外のセッションでは Claude Code 自身が分類器を呼び、API・Enterprise ではトークン使用量に数えられる。Pro / Max / Team では課金されない。判断 1 回ごとに往復が 1 つ増えるため遅延はある。読み取りと作業ディレクトリ内の編集は審査の対象外
  • 拒否が 3 回連続、または計 20 回に達すると、ユーザー確認のモードに戻る
  • 分類器は隔離境界ではない。無人実行では隔離環境の併用が推奨される
bypass モード

--dangerously-skip-permissions（bypassPermissions）は確認ダイアログと安全チェックを省略する。ツール呼び出しは即時実行される。残るのは、ask ルールによる確認と、ホームやルートの削除など「どのモードでも自動承認されない操作」の確認または拒否だけである。ローカルの実プロジェクトでの使用は推奨されない。

5-5. サンドボックス（Sandboxing）

サンドボックスは、コマンドを隔離された環境で動かし、その外のファイルやネットワークに触れさせない仕組みである。制限するのは OS なので、モデルが何を実行しても効く。macOS・Linux・WSL2 で使え、ネイティブ Windows では使えない。有効化は /sandbox か、settings.json の sandbox キー。

{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "denyRead": ["~/.ssh", "./secrets"]          // サンドボックス内から読めない場所
    },
    "network": {
      "allowedDomains": ["registry.npmjs.org", "github.com"]  // 通信してよい先
    }
  }
}
実行場所対象
サンドボックス内
  • Bash・PowerShell・Monitor のコマンド
  • 上記の子プロセス（npm install が走らせるスクリプトなど）
サンドボックス外
  • Read / Edit などのファイルツール、MCP サーバー、フック
  • excludedCommands に一致するコマンド
  • サンドボックスで失敗した後の再実行。default / acceptEdits では確認が出る。allowUnsandboxedCommands: false で禁止できる
  • ユーザーが ! で打ったコマンド
  • 権限ルールが見るのは cat .env というコマンドの文字列。サンドボックスが見るのは、実行中のプロセスが実際に開いたファイルや接続先。だから python3 app.py の中で .env を開いても止まる
  • サンドボックス内から書き込めるのは、作業ディレクトリ・一時ディレクトリ・--add-dir で追加した場所だけ。外への書き込みや削除は OS が拒否する
  • autoAllowBashIfSandboxed（既定 true）で、サンドボックス内の Bash は確認なしで実行される。確認を減らす手段であり、隔離境界ではない

プロセス全体を隔離する選択肢

方式（上ほど広く包む）隔離されるもの備考
VM / クラウドセッションOS 全体最も強い
dev container開発環境全体Docker が必要
Sandbox runtime（srt claude）Claude Code プロセス全体。ファイルツール・MCP・フックを含むDocker 不要。ベータ
サンドボックス（本節）シェルコマンドだけ設定だけで使える

bypass モードは、コンテナ・VM・Sandbox runtime の中で動かすことが公式に推奨されている。

5-6. フック（Hooks）

フックは、決まったタイミングで必ず実行される、ユーザーが用意したプログラムである。権限ルールが許可・確認・拒否しかできないのに対し、検証・整形・通知など任意の処理を差し込める。ルールの「拒否」にあたる動作を、フックでは「ブロック」と呼ぶ。

イベントタイミングできること
PreToolUseツール実行前ブロック・入力の書き換え。権限ルールより先に判定
PostToolUseツール成功後（失敗時は PostToolUseFailure）整形・Lint・テスト。結果をモデルに返せる。取り消しは不可
UserPromptSubmitプロンプト送信直後ブロック。秘密情報の貼り付け検出、コンテキストの追加
Stop応答終了時（ユーザーの中断では発火しない）継続を指示。テストが通るまで終了させない
PermissionRequest確認ダイアログ表示時ユーザーの代わりに許可・拒否
SessionStart開始・再開時ブランチ名や Issue をコンテキストに投入
SessionEnd終了時後片付け・統計の記録。会話記録（transcript_path）の usage からトークン数を集計できる。モデルには返せない
InstructionsLoadedCLAUDE.md・rules 読み込み時読み込まれた指示の診断

書き方

設定ファイルの hooks に、イベント → 対象ツール（matcher）→ 実行するコマンドの順で書く。登録状況は /hooks で見る。例は「モデルがファイルを編集するたびに、そのパスをログに残す」。

{
  "hooks": {
    "PostToolUse": [                          // いつ：ツールが成功した後
      {
        "matcher": "Write|Edit",                // どのツールで：Write か Edit
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' >> .claude/edited.log"   // 何を：stdin の JSON からパスを取り出して追記
          }
        ]
      }
    ]
  }
}
項目意味
入力stdin に JSON（ツール名・引数など）
exit 0通過
exit 2ブロック。stderr の内容がモデルへのフィードバック
それ以外フックのエラー。ブロックしない
onFailureフック自体が失敗（クラッシュ・タイムアウト）したときの扱い。"continue"（既定）は操作を通す、"block" はブロックする
  • フックで deny ルールは覆せない
  • stderr には理由と代替案を書く。モデルはそれを読んで次を決める
  • command（シェル）と http（POST）が基本。ほかに mcp_tool・prompt・agent 型があり、prompt / agent はモデルが判定するので保証がない
  • フックはサンドボックスの外で動く。他人のフックは中身を読んでから使う
  • 1 行で済まない処理はスクリプトファイルにする。.claude/hooks/ に置き、$CLAUDE_PROJECT_DIR を起点にしたパスで指定する

レシピ A：rm -rf を理由付きでブロックする

.claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-rm.py",
            "onFailure": "block"       // 既定の "continue" だとスクリプト自体の失敗時に通ってしまう
          }
        ]
      }
    ]
  }
}
.claude/hooks/block-rm.py
import json, sys

# stdin の JSON から、実行されようとしているコマンドを取り出す
cmd = json.load(sys.stdin)["tool_input"]["command"]

# 理由を stderr に書いて exit 2 すると、実行がブロックされる
if "rm -rf" in cmd:
    print("rm -rf は禁止。削除するファイルを個別に指定すること", file=sys.stderr)
    sys.exit(2)
モデルが出したコマンド結果
rm -rf buildブロック。stderr の文がモデルに返る。モデルは rm build/main.js のように個別の削除に変える
rm build/main.js通過。続けて権限ルールとモードで判定される

レシピ B：テストが通るまで終了させない

.claude/settings.json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/require-tests.py"
          }
        ]
      }
    ]
  }
}
.claude/hooks/require-tests.py
import json, subprocess, sys

# すでにこのフックで継続中なら、無限ループを避けて終了を許す
if json.load(sys.stdin).get("stop_hook_active"):
    sys.exit(0)

# テストが失敗していたら、理由を stderr に書いて exit 2（終了をブロック）
if subprocess.run(["npm", "test"]).returncode != 0:
    print("テストが失敗している。修正してから終了すること", file=sys.stderr)
    sys.exit(2)
応答を終えようとしたとき結果
テストが失敗しているブロック。モデルは stderr の文を読み、修正を続ける
テストが通っている終了

stop_hook_active は「すでに Stop フックで継続中」を示す。これを確認しないと無限ループになる。Claude Code 側にも、Stop フックによる継続は連続 8 回までという上限がある。

5-7. 組織の管理設定（Managed settings）

管理設定はユーザー設定・プロジェクト設定・コマンドラインのいずれでも上書きできない。技術的な強制は管理設定、行動指針は管理 CLAUDE.md と役割を分ける。

目的キー
bypass の禁止permissions.disableBypassPermissionsMode: "disable"
auto の禁止disableAutoMode: "disable"（permissions. 配下でも可）
組織のルールだけを有効化allowManagedPermissionRulesOnly。ユーザー・プロジェクト・ローカル設定の allow・ask・deny を無視
組織のフックだけを有効化allowManagedHooksOnly
機密パス・危険コマンドの禁止permissions.deny / sandbox
スキルのシェル実行の禁止disableSkillShellExecution

managed-settings.json の配置先は OS ごとに決まっている。

  • macOS：/Library/Application Support/ClaudeCode/
  • Linux・WSL：/etc/claude-code/
  • Windows：C:\Program Files\ClaudeCode\

5-8. 多層防御の実践（Defense in depth）

多層防御の必要性

2026 年 9 月のユーザー投稿。「進めて」と頼まれた Claude Code が、Gmail の未読契約書に PC 内の署名画像を貼り、送信直前まで進めた。モデルは頼まれていない操作を「良かれと思って」選ぶ。送信ツールに ask ルールがあれば確認で止まるが、送信の経路をすべてルールで列挙することはできない。そのため、1 つの手段に頼らず層を重ねる。

公式は、権限ルール・権限モード・サンドボックスを互いに補い合う（complementary）ものとしている。権限ルールとフックは、実行前にコマンド文字列や引数で判定する。サンドボックスは、実行中のプロセスを OS の力で止める。管理設定は、それらの設定を固定する。見ている対象が違うので、重ねると穴が埋まる。

例：ホームディレクトリを消させない

Bash(rm -rf *) の deny とサンドボックスを両方設定したとき、操作ごとに止まる場所が変わる。

モデルが試みた操作止める層理由
rm -rf build/権限ルールdeny がコマンド文字列に一致する
rm -r ~/ユーザー確認deny の rm -rf * には一致しない。ただしホームなど重要な場所の削除には組み込みの確認が出る（default / acceptEdits。dontAsk では拒否）
./cleanup.sh（中で rm -rf ~/）サンドボックススクリプトの中身はルールに見えない。作業ディレクトリ外の削除を OS が拒否する
失敗後に「サンドボックス外で再実行」を求めるユーザー確認default / acceptEdits では再実行前に確認が出る。allowUnsandboxedCommands: false で禁止できる

ルールだけではスクリプトの中身を止められない。サンドボックスだけでは作業ディレクトリ内の削除を止められない。2 つ重ねて初めて穴が塞がる。設定は deny を先に書き、allow は後から追加する。

5-9. 章のまとめ

  • モデルはツール呼び出しを書くだけ。実行と判定はハーネスが行う
  • 指示（ソフト制御）に保証はない。守らせたい規則は設定に書く
  • 判定順：フック → 権限ルール → 権限モード → ユーザー確認 → 実行
  • 権限ルールはコマンド文字列、サンドボックスはプロセスを見る
  • 日常作業は、編集を後から git diff で確認する運用なら acceptEdits、確認を減らすならサンドボックス併用の auto。無人実行はコンテナや VM の中で行う
  • チーム共通の規則は .claude/settings.json に書いてコミットする。組織として強制する規則は管理設定に書く
  • 1 つの手段ですべてを守ろうとしない。見える範囲の違う手段を組み合わせる（ルール + サンドボックスなど）
